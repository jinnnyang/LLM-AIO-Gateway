# 空回复问题与「空回复重试/告警」设计备忘

> **状态**：已知问题记录 + 未实现的功能设想。本文档不描述已落地的行为，仅记录 2026-08-28 实测发现的现象、根因、以及将来若要做「空回复重试/告警」需要注意的设计约束。
>
> **来源**：验证网关中转能力时在 `vcp/kimi-k2-250905` 上偶然发现，非专项排查。

---

## 1. 现象

用合法网关 key 请求 `vcp/kimi-k2-250905`（火山方舟 coding-plan 端点），`max_tokens: 32`：

- HTTP **200**
- `usage.completion_tokens: 32`（**满额计费**）
- `choices[0].message.content`: **`""`**（空字符串）
- `choices[0].message.reasoning_content`: 有内容，但被截断在句子中间
- `choices[0].finish_reason`: **`"length"`**

即：**请求成功、产生了计费、但客户端拿到零可用输出**。

### 实测对照

| 模型 | max_tokens | finish_reason | content | reasoning_content | completion_tokens |
|---|---|---|---|---|---|
| `vcp/kimi-k2-250905` | 32 | `length` | `""` | 有（截断） | 32 |
| `vcp/kimi-k2-250905` | 512 | `stop` | `收到` | 有（完整） | 68 |
| `vcp/deepseek-v4-flash-260425` | 32 | `stop` | `收到` | — | 97（含上游隐式思考）|
| `vcp/ark-code-latest` | 32 | `stop` | `收到` | — | 32 |

流式（`stream: true`, `max_tokens: 32`）下同一模型的 SSE chunk 序列证实了机制：

```
delta: {"role": "assistant"}
delta: {"reasoning_content": "We"}
delta: {"reasoning_content": " need"}
delta: {"reasoning_content": " respond"}
...            ← 全部 32 个 token 都花在 reasoning_content 上
               ← 没有任何一个 delta 带 content
```

## 2. 根因

**这不是网关缺陷，是推理模型（reasoning model）的 token 预算耗尽。**

`kimi-k2` 是思考型模型，先输出 `reasoning_content`（思维链）再输出 `content`（正式回答）。`max_tokens` 同时约束这两者之和。当 `max_tokens` 太小，预算在思维链阶段就被耗尽，模型还没进入正式回答阶段就被硬截断，于是 `content` 为空。

`max_tokens=512` 时同一模型正常返回 `收到`，`completion_tokens=68`（思维链约 60 + 正文 2）。**可复现、可解释、非随机故障。**

因此这是**上游模型行为**，网关如实转发了上游返回的一切（`content=""`、`reasoning_content`、`finish_reason=length`、真实 usage），没有丢字段、没有篡改。从「忠实代理」角度网关是正确的。

## 3. 为什么它仍然值得被网关关注

尽管不是 bug，这个组合对网关用户是**有害的成功**：

1. **计费但无产出**：`completion_tokens=32` 是真实扣费的。客户端付了钱拿到空串。
2. **HTTP 200 骗过所有重试逻辑**：客户端 SDK、上层应用、以及网关自身的 fallback 机制都以「是否抛异常 / 状态码」判断成败。200 + 空内容会被一致判定为「成功」，不会触发任何补救。
3. **fallback 策略完全绕过**：见下节。
4. **静默难查**：用户视角是「模型不回话」，但日志里是一次成功请求，无 error 字段可查。

## 4. 当前网关的处理现状（代码事实）

### 4.1 空 content 会被原样透出

`app/adapters/output.py:32-33`：

```python
content = strip_think_tags(attr(message, "content", "") or "")
reasoning = attr(message, "reasoning_content", None) or ""
```

`app/protocols/egress.py:550-552`：

```python
resp_msg = {"role": output.role or "assistant", "content": output.text}
if output.reasoning:
    resp_msg["reasoning_content"] = output.reasoning
```

`output.text` 为空串时照样写入 `content`，**无任何空值检查或告警**。全仓 grep `empty_response` / `is_empty` / `not content` 在 `app/core/` 与 `app/adapters/` 下**零命中** —— 网关目前没有任何「空回复」概念。

### 4.2 fallback 机制无法覆盖此场景

fallback 触发器默认集合，`app/db/fallback.py:8-14`：

```python
DEFAULT_TRIGGERS = {
    "timeout": True,
    "connection_error": True,
    "http_429": True,
    "http_5xx": True,
    "http_4xx": False,
}
```

触发器由 `classify_upstream_error(exc)` 产出（`app/services/routing_targets.py:37`），该函数**签名即要求一个 `Exception`**。空回复场景下上游返回 200、不抛异常，`classify_upstream_error` 根本不会被调用，`apply_fallback_policy` 也就拿不到 trigger。

**结论：现有 5 个 trigger 全部是「传输层/状态码层」信号，没有任何「内容层」信号。空回复对 fallback 系统是不可见的。**

### 4.3 唯一的例外：Responses 协议的流式空响应

`app/protocols/egress.py:361-362` 有一处内容层检查：

```python
if not saw_message_done and not accumulated_text and not accumulated_reasoning and not tool_states:
    raise RuntimeError("upstream closed before sending response output")
```

但它**管不到本案**，因为：
- 只在 Responses 协议的流式路径（不覆盖 `/v1/chat/completions`）
- 条件是 `not accumulated_reasoning` —— 本案 reasoning 有内容，条件不成立
- 语义是「上游连接提前断开」而非「预算耗尽导致正文为空」

## 5. 若要实现「空回复重试/告警」的设计约束

以下是设想，**尚未实现**，记录下来避免将来踩坑。

### 5.1 判定条件必须收紧，不能简单判 `content == ""`

空 `content` 在很多情况下是**完全合法**的，误判会造成重复计费和错误重试：

| 场景 | content | 是否异常 |
|---|---|---|
| 纯 tool_call 回复 | `""` | **正常**，内容在 `tool_calls` 里 |
| reasoning 预算耗尽（本案） | `""` | 异常 |
| 上游连接提前断开 | `""` | 异常 |
| 模型主动返回空（如内容审核拦截） | `""` | 取决于产品定义 |
| 多模态图像回复 | `""` | 视实现而定 |

建议的判定式（草案）：

```
异常空回复 ≡ content 为空
            AND tool_calls 为空
            AND (finish_reason == "length" OR 未收到 message_done)
            AND completion_tokens > 0
```

`tool_calls 为空` 这一项**不可省略** —— 否则所有工具调用轮次都会被误判为空回复并触发重试，这会破坏 agent 类客户端的每一次工具交互，是最危险的误伤。

`completion_tokens > 0` 用于区分「产生了计费但无产出」（值得管）和「上游根本没干活」（属连接问题，另有路径）。

### 5.2 `finish_reason == "length"` + 空 content 时，重试策略不能是「原样重发」

原样重发会**再次**用同样的 `max_tokens` 打同一个模型，得到同样的空回复，只是把计费翻倍。这是最容易写错的地方。

可行方向（需产品决策）：
- **提高 max_tokens 重试**：网关自动放大 `max_tokens` 后重试一次。但这违反客户端显式指定的参数，属于「网关擅自改写请求」，需要显式开关。
- **切换到非思考模型**：走 fallback chain 到不消耗思维链预算的模型（如 `ark-code-latest`）。语义上最干净，但要求用户配置了合适的 chain。
- **只告警不重试**：最保守，把决策权交回客户端。

### 5.3 若接入 fallback 系统，需要新增内容层 trigger

现有架构下需要的改动点：

1. `app/db/fallback.py` 的 `DEFAULT_TRIGGERS` 新增 `"empty_response": False`（**默认关闭**，因为它涉及重复计费，属于破坏性行为，必须用户显式开启）
2. `classify_upstream_error(exc)` 只吃 `Exception`，无法承载「200 但内容为空」。需要**另一条判定通路**，而不是把空回复硬塞成一个伪异常 —— 后者会污染错误分类语义，也会让日志里出现不存在的错误。
3. `app/router/proxy.py` 的成功路径（非异常路径）需要在拿到 `InternalOutputMessage` 后、渲染响应前插入检查点。当前该位置**没有** fallback 调用，`apply_fallback_policy` 的 9 个调用点全在异常处理或前置路由决策中。
4. 流式路径更麻烦：SSE 已经开始向客户端吐 chunk 后才发现正文为空，此时**无法回滚已发送的响应头和 chunk**。流式下大概率只能告警、不能重试。

### 5.4 告警比重试更容易做且风险低

若只做告警（不改变请求行为），改动面小得多：
- 在 `app/protocols/egress.py:540` 的 `render_chat_completion` 已有的 debug 日志处升级日志级别：该函数已经在打印 `text_chars=%d reasoning_chars=%d tool_calls=%d`，判定所需信息**全部就位**，只需加条件判断和 `warning` 级输出。
- 计入 `request_logs` / 统计面板，让「空回复率」成为一个可观测指标。
- 不触碰计费、不重发请求、不改写客户端参数 —— 无副作用。

**建议：如果要做，先做告警和可观测性，重试作为独立的后续决策。**

## 6. 复现方法

```bash
curl -X POST http://127.0.0.1:8001/v1/chat/completions \
  -H "Authorization: Bearer <网关 key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"vcp/kimi-k2-250905","messages":[{"role":"user","content":"只回复两个字：收到"}],"max_tokens":32}'
```

预期：200 + `content: ""` + `finish_reason: "length"` + `reasoning_content` 有截断内容。

把 `max_tokens` 改成 512 即恢复正常，可用于对照。

> 注：本项目在 Windows 上运行，WSL 侧无法访问 Windows 的 localhost（WSL2 NAT），HTTP 复现须从 Windows 侧执行。

## 7. 不建议做的事

- **不要**把空回复判定写成 `if not content: raise`。会击穿所有 tool_call 轮次。
- **不要**复用 `classify_upstream_error` 承载内容层信号。它的契约是「异常 → 传输层分类」，混入内容语义会让 `http_4xx` / `timeout` 这些分类失去准确性。
- **不要**默认开启空回复重试。它会在用户不知情的情况下产生双倍计费。
- **不要**在流式路径尝试重试。响应已部分送达，无法回滚。
- **不要**把 `kimi-k2` 的这个行为当成需要"修复"的网关 bug 去改适配器。上游行为正确，网关转发正确，缺的只是可观测性。

litellm.NotFoundError: NotFoundError: OpenAIException - The requested model does not
support the coding plan feature. Please refer to the documentation at

这是火山方舟 coding-plan 端点（`/api/coding/v3`）的模型白名单限制，v3 系列旧模型不在其中，v4 全系（`deepseek-v4-flash-260425`、`deepseek-v4-pro-ga-260813`）与 `ark-code-latest`、`kimi-k2-250905` 均正常。**非网关问题**，且上游 message 被原样透出，可诊断性良好。

一个可选的改进点（未实施）：上游 4xx 目前一律映射为网关 500。按 OpenAI 兼容语义，上游认证/404 类错误透传 502 更利于客户端区分「网关故障」与「上游拒绝」。此项涉及错误码契约变更，需单独评估对现有客户端的影响。
