# 模型能力元数据扩展 · 设计方案

> 状态：**设计稿，仅规划，不实现**（已完成四轮评审：专家评审 + 设计评审一轮 + 用户补充 review + 设计评审二轮/三轮处置）
> 分支：main → 新功能分支（feature/model-metadata）
> 对应任务：新增模型参数 context_length / max_output_tokens / input_modalities / output_modalities / input_price / output_price / cached_input_price，服务于后续多模态转发、分流中间件、计费。

---

## 1. 背景与目标

### 1.1 现状
- 模型存于 `provider_models` 表（`app/database.py:347`），字段：`provider_id / model_id / model_name / enabled / preprocessor / image_generation / source(auto|custom) / responses_*`。
- **无** context_length / max_tokens / price / modalities 任何字段。
- discovery（`app/services/discovery.py`）只探测模型 **ID 和名称**，不探测能力。
- 路由（`prepare_request_policy`）**不读**模型元数据做转发决策。

### 1.2 目标
为每个模型维护一套能力元数据，支撑三个后续功能：
1. **多模态转发**：按用户消息附带（图片/音频/视频）的模态，匹配支持该模态的模型。
2. **分流中间件**：按请求 token 长度 vs 模型 context_length，决定是否分流/超窗。
3. **计费**：按实际 usage 计算每次请求成本。

**计费价格来源（定案 13）**：计费 = 单价 × 用量。单价即本表 `input_price/output_price/cached_input_price`（`$/M token`，由三源同步）。**多模态的"贵"已由供应商在 usage 上报时折算成 token 数**（图片按像素折 token、音频折 token），故**无需 per-modal 单价或跨单位（秒）拆分**。精确公式（注意 `$/M token` 单位需除以 1e6）：

```
cost = input_tokens  × input_price        / 1e6
     + output_tokens × output_price       / 1e6
     + cached_tokens × cached_input_price / 1e6
```

### 1.3 新增字段（存 `$/M token` 绝对定价）
| 字段 | 类型 | 含义 |
|------|------|------|
| `context_length` | INTEGER (NULL) | 模型上下文窗口（token） |
| `max_output_tokens` | INTEGER (NULL) | 模型最大输出（token）。**命名对齐 models.dev `limit.output`，避免与 `preprocessors` 表既有 `max_tokens` 列（database.py:379）歧义** |
| `input_modalities` | TEXT(JSON 数组) | 支持的输入模态：`text / vision / video / audio / image / ...` |
| `output_modalities` | TEXT(JSON 数组) | 支持的输出模态：`text / vision / video / audio / embedding / ...` |
| `input_price` | REAL (NULL) | 输入价 `$/M token` |
| `output_price` | REAL (NULL) | 输出价 `$/M token` |
| `cached_input_price` | REAL (NULL) | 缓存输入价 `$/M token`（NULL = 无缓存价） |

> **命名说明**：字段采用行业通用术语 **modalities**（模态）。DB 列名落地前确定，避免落地后 `ALTER TABLE RENAME COLUMN` 高成本迁移。

> **`context_length` 单标量（不做 per-modal 分档）**：部分模型上下文随模态变化（如 Gemini 文本窗口与含音频/视频时不同）。本设计**不拆分**——取各源**典型/最大窗口**（保住文本场景性能，参考 OmniRoute 取舍），不做 `context_lengths` 按模态分档。
> **⚠️ 风险**：当多媒体请求实际可用窗口 < 配置的最大窗口时，路由层窗口检查会**误判为未超窗**，请求到上游后可能返回 400。后续路由处理预案（本次不实现）：超窗后 **fallback 到支持更大窗口的模型**，或**重试前截断**。

> **不设 `metadata_sources` / `metadata_status` 列**：字段来源由 `source`（auto/custom）判断足够；采集失败留 NULL、下次刷新重试；不做来源/状态落库。依赖这两列的逻辑已逐条改为不依赖列的替代实现（见 §2.1/§2.3/§4.2）。

## 2. 数据源与匹配工具（核心设计）

### 2.1 统一口径
- **价格一律存 `$/M token` 绝对价**（与项目 07 号文档口径一致）。
- **仅考虑美元**；不做币种换算（人民币兑美元等搁置）。所有源须显式断言返回 USD。
- **models.dev 可靠性声明**：models.dev 官方明确 *"Do not treat this as runtime truth"*——数据可能不准确、不实时。其数据**仅供参考**，不保证与供应商实际 API 一致；**高精度场景（尤其计费）应以供应商官方定价为准**，元数据仅作缺省估算。OpenRouter 同理。
- **价格单位归一化**：三源表示不一（models.dev 已 $/M、OpenRouter per-token 字符串、LiteLLM per-token/per-1k 浮点），**按字段名分支换算**：`per_token→×1e6`、`per_1k→×1e3`、已 $/M 勿二次换算、OpenRouter 先 `float()`。
- **价格合并（三轮定案 4）**：**三源（models.dev ‖ OpenRouter ‖ LiteLLM）始终并行合并**（LiteLLM 本地零成本，无理由只在降级时用，见 §2.3）：
  - **候选数 ≥3 → 取中位数**（抗单源异常，交叉验证真正生效）。
  - **候选数 = 2 → 取较高价（保守 = 不亏钱）**；两价冲突 >20% 记 **WARN** 日志（含模型 ID 与候选值便于批量排查，如 `WARN price conflict model=xxx candidates=[0.15, 0.30] picked=0.30`）。低价常是过期数据，低估比高估对网关运营风险更大。注意 =2 分支常落在国产/冷门模型上（models.dev 与 OpenRouter 数据质量最不稳定处），WARN 量可能不小，**按模型 ID 归组排查**。
  - **候选数 = 1 → 单源直接采用**。
  - cached 价独立处理且允许缺省（三源字段名各不同：models.dev `cost.cache_read`、OpenRouter `pricing.input_cache_read`，勿混淆 request 费）。
  - **>10x 偏离仅记日志告警，不落库**——**接受此降级：异常价格仅在日志可见，管理员需主动排查**（三轮 #10 定案）。
  - **中位数固有局限（四轮备注）**：中位数假设"多数源正确"；若两源同时陈旧会压过正确值（如 models.dev 与 LiteLLM 都停在旧价、OpenRouter 已降价）。LiteLLM 为打包静态字典，陈旧度取决于 pip 版本，**建议 requirements 保持 litellm 较新版本**（四轮 #2 定案）。
- **embedding 特殊处理**：`output_modalities` 含 `embedding` 时，只有 `input_price` 即可参与合并，不适用"须含双价"门槛（仅合并 modalities 之后判断，见 §2.3 顺序）。
- **网络数据源为必需**（models.dev / OpenRouter），LiteLLM 本地始终参与合并（兜底 + 第三候选）。

### 2.2 数据源优先级与字段覆盖
| 数据源 | 覆盖 | 获取方式 | 说明 |
|--------|------|----------|------|
| **models.dev** | context / max_output_tokens / 价格 / modalities | HTTP API（`https://models.dev/api.json`，provider 维度；必要时交叉引用 `models.json` 模型维度） | **主源**，覆盖广；仅供参考 |
| **OpenRouter** | 同 models.dev | HTTP API（`https://openrouter.ai/api/v1/models`） | **主源**，覆盖广；仅供参考 |
| **LiteLLM `model_cost`** | context / max_output_tokens / 价格 / mode / 部分 supports_vision | 本地库 `litellm.model_cost`（已验证 3213 模型） | **始终参与**（本地零成本），离线兜底 |
| **供应商 `/models`** | **modalities-only**（火山新版有） | 各 provider API | **独立的模态补充源**：只覆盖 modalities、不含价格；**不参与价格候选计数，不影响降级判定**（三轮 #3 定案） |
| **手工填** | 全部 | 编辑页手动 | custom 模型 / 无外部源的兜底 |

### 2.3 匹配工具设计（`app/services/model_metadata.py`）
**职责**：给定 `(provider, model_id)` → 合并各源 → 输出统一元数据。

```
输入: provider, model_id（入口先归一化）
  ├─ LiteLLM model_cost 查（本地，始终参与）
  ├─ models.dev / OpenRouter 查（网络，L1 缓存，可禁用/超时）
  └─ 供应商 /models（modalities-only 补充，auto 可选，不含价格）
  ↓
① modalities 合并（白名单并集）
  ↓
② 判断 output_modalities 是否含 embedding
  ↓
③ price 合并（按 §2.1：≥3 取中位数 / =2 取较高价 / =1 单源）
  ↓
输出: 统一元数据 dict（采不到即 NULL/空，留待下次刷新重试）
```

**合并与降级（三轮严重项定案，方案 A）**：
- **三源始终并行合并**：models.dev ‖ OpenRouter ‖ LiteLLM 同时取数。LiteLLM **始终参与**（本地零成本），正常场景三源交叉验证，`≥3 取中位数` 分支**活**。
- **整级降级（修正）**：网络源全失败 → 仅剩 LiteLLM（单源直接采用）；**三源全失败 → 空候选（字段留 NULL，下次刷新重试）**。不再有"网络源失败才启用 LiteLLM"的互斥，因此中位数分支非死代码。
- **供应商 `/models`**：独立的 modalities-only 补充源，**不参与价格候选计数、不影响上述降级判定**。

**关键规则**：
- **逐源适配器**：三个源字段结构/单位/词汇各不相同，**不可共用同一字段名解析逻辑**。`_from_models_dev` / `_from_openrouter` / `_from_litellm` 各自独立解析；**来源仅记日志，不落库**。实测字段位置：models.dev 上下文在 `limit:{context,output}`、模态在 `modalities:{input,output}`；OpenRouter 上下文在 `context_length`、模态在 `architecture.{input_modalities,output_modalities}`、价格为 per-token 字符串。
- **模态取并集（白名单宁漏勿虚）**：跨源词汇不统一，先做归一化映射（`image↔vision`、`pdf/file` 归类），再按**白名单过滤**——仅当某源官方 capability 明确声明该模态才加入，未声明的模态一律不加入。宁可漏报（可回退），不虚报（避免错路由）。**`mode='chat'/'embedding'` 推断仅兜底展示，不参与路由决策**。
- **无源回退**：全部无源 → 字段保持 NULL/空，不猜。采集失败留 NULL，`source=='auto'` 的模型随下次 refresh 自动重试。
- **匹配归一化**：model_id 归一化规则（优先级）：① 去 provider 前缀（`vcp-`、`openai/`、`anthropic.`）② 去日期/版本后缀（`-latest`、`-20240229`、`-0125`、`-1106-preview`）③ 小写 ④ 无法匹配时记日志、不阻断。LiteLLM model 名常带 provider 前缀/别名，需建别名归一表。

### 2.4 触发时机（重要区分）

**auto 模型（自动发现）**：随 `refresh_provider_models` 一起，discovery 命中时**自动调用匹配工具**填充能力字段。刷新是幂等 upsert。

**custom 模型（手工添加）**：**不自动更新**。仅在**编辑页弹窗里的「同步」图标按钮**触发——用户点一下，才调匹配工具拉取填充。
- **只填空的字段**：同步结果仅填充当前仍为 NULL/空的字段，**已填写的保留**（不覆盖用户改动）。提供「覆盖全部」勾选可选。
- **"只填空"规则在前端实现**（同步按钮拉候选 → 前端按只填空合并 → 统一走 `PUT capabilities` 写库，见 §4.3/§4.4）。

> 这满足你「自动拉取模型自动填充、手动模型按需同步」的设计。

```sql
ALTER TABLE provider_models ADD COLUMN context_length INTEGER;
ALTER TABLE provider_models ADD COLUMN max_output_tokens INTEGER;
ALTER TABLE provider_models ADD COLUMN input_modalities TEXT NOT NULL DEFAULT '[]';
ALTER TABLE provider_models ADD COLUMN output_modalities TEXT NOT NULL DEFAULT '[]';
ALTER TABLE provider_models ADD COLUMN input_price REAL;          -- 必须 REAL 且允许 NULL（勿 DEFAULT 0），区分"未采集"与"真为 0"
ALTER TABLE provider_models ADD COLUMN output_price REAL;
ALTER TABLE provider_models ADD COLUMN cached_input_price REAL;
```
- 迁移用幂等模式：查 `PRAGMA table_info(provider_models)`，缺列才 ALTER（并入 database.py 现有字典化迁移函数，init_db 串行链 executescript 之后）。**迁移 DEFAULT 必须与 CREATE TABLE 完全一致**，否则新旧库行为分叉。
- 新装库直接在 `CREATE TABLE` 定义里加列。
- 价格列**禁止 `NOT NULL DEFAULT 0`**：0 会被计费/中位数误当真实价格。
- 读取端对 modalities 须 `json.loads` 并容错空串/非法 JSON。
- **索引备注（三轮 #8 定案）**：`modalities` 存 JSON TEXT，**无法索引**，后续"多模态转发"若需 `WHERE input_modalities 含 'audio'` 只能全表扫 + Python 过滤。当前 ≤1000 行无碍；未来若需索引化，考虑 `model_modalities` 关联表或 SQLite JSON1 表达式索引。

> 扩展后总表 = 16 原有列 + 7 新列 = **23 列**。约束（`UNIQUE(provider_id, model_id)`、FK 级联、`idx_provider_models_model_id`）不变。

## 4. 后端改动设计

### 4.1 `app/services/model_metadata.py`（新）
- `resolve_model_metadata(provider_id, model_id) -> dict`：匹配工具主入口（§2.3）。**入口先归一化 `model_id`**。
- 内部：
  - `_from_litellm(model_id)`：查 `litellm.model_cost`，归一化匹配（**始终参与**）。
  - `_from_models_dev(model_id)` / `_from_openrouter(model_id)`：HTTP 拉取（可配置超时/缓存/开关）。
  - `_normalize_model_id()`：跨源匹配归一化（§2.3 规则优先级）。
  - `_merge_price()`：三源价格合并（§2.1：≥3 取中位数 / =2 取较高价 / =1 单源）。
  - `_merge_modalities()`：模态白名单并集（**先于 price 合并**，供 embedding 判断）。

**两级缓存**：
- **L1**：全量 JSON 列表（models.dev / OpenRouter），TTL 24h，**惰性加载**。L1 过期才触发网络请求；全量 JSON 变化低频，24h 足够且防限流。
- **L2**：单模型匹配结果，TTL 5–10min，键 `(provider_id, model_id)`（**用归一化后的 `model_id`**），**写库成功后主动失效**对应键（DB 变化是唯一失效源）。
- **层级约束**：L2 只消费 L1，**绝不自发发网络请求**；单模型缓存过期后从 L1 重算而非拉网。单进程无碍，**多 worker 下 L1/L2 各自为政，需标注限制**。

### 4.2 `app/services/discovery.py` 增强
`refresh_provider_models` 的 upsert 处（INSERT/UPDATE），对 **auto 模型**自动调用 `resolve_model_metadata` 填充能力字段。**custom 模型不动**。要点：
- **批量预取**：勿在 for 循环内逐模型 await（几百模型会卡单连接）。在循环外用 `asyncio.gather`（受现有 `asyncio.Semaphore(4)` 限流）批量预取全部候选能力再一次性写入。`_from_litellm` 走本地表零成本，仅网络源需预取。
- **INSERT 语句需同步扩展**：现有 `INSERT OR IGNORE INTO provider_models (provider_id, model_id, model_name, enabled, source) VALUES (?, ?, ?, 1, 'auto')`（discovery.py:174）迁移后靠 DEFAULT 填充，但 M2 接入后此语句须扩展为写入 metadata 字段，否则新发现模型不带能力数据。
- **降级**：单模型 resolve 异常必须 `try/except` 继续并保留旧值（字段留 NULL，下次刷新重试），**绝不让单模型失败使整个 refresh 回滚**（当前外层 try 粒度太粗）。**"重复请求浪费"由 L1 缓存化解**——resolve 走 24h L1 缓存，不会每次 refresh 都发网。
- **覆盖规则**：无来源记录后，简化为——**auto 模型 refresh 总是覆盖（幂等 upsert，值相同）；custom 行由 `source=='auto'` 守卫，绝不碰**。
- **custom 守卫**：custom/auto 同 id 时，能力字段必须与 `source=='auto'` 同守卫，避免污染 custom 行。

**并发安全**：现有 `_lock`（threading.Lock）**仅在 `init_db` 建表时用**（database.py:32），**不保护 CRUD**；`get_db`（database.py:282）不持锁，SQLite 只在写事务级别序列化，读不阻塞。处置：**引入 per-provider `asyncio.Lock`**（map[provider_id] → asyncio.Lock）保护对同一 `provider_id` 的 refresh/sync 读写；`PUT /capabilities` 是 custom 单行、与 auto refresh 不同行，竞态风险低，可仅靠 SQLite 写事务。
> **限制（三轮 #6 定案）**：① `asyncio.Lock` **只在同一事件循环内生效**——FastAPI 的 `def`（非 async）端点跑在 threadpool，**不参与** asyncio.Lock 排队（已承认 PUT 靠 SQLite 写事务）；② **多 worker（gunicorn -w N）下完全失效**——各进程独立 Lock 对象。接受残余竞态（auto 值相同，仅 `updated` 计数可能偏差），如实标注。

### 4.3 API：候选查询端点（只读）
- `GET /admin/providers/{id}/models/{model_id}/metadata-candidates`
  - 入参：provider_id, model_id
  - 逻辑：调 `resolve_model_metadata`，**只返回候选值与"将被覆盖的现有值"供前端 diff，不写库**。
  - 权限：必须 `require_admin_session`。
  - 前端「同步」按钮调用，弹结果，用户确认/覆盖后提交。
- **为何只读**：候选查询是纯查询，语义上用 `GET`（三轮 #5 定案，改自 `POST .../sync-metadata`，且**删掉 `?apply=true`**——写库统一走 `PUT capabilities`，职责单一，避免两条写路径重复实现"只填空"，三轮 #4 定案）。

### 4.4 API：写库端点
- `PUT /admin/providers/{id}/models/{model_id}/capabilities`
  - **唯一写库路径**（三轮 #4 定案）：模型的能力字段一律由此写入。**custom 与 auto 行均可写**（实现期变更，见文末「实现期偏离」）：auto 行的手填值会在下次上游 refresh 时被覆盖（refresh 拥有 auto 行的数据所有权），custom 行的值永久保留。
  - ModelInfo 扩 Optional 字段，按键存在才写（勿用 `m.get(..., None)` 误写 NULL 丢值）。
  - **"只填空"由前端实现，后端 `mode=fill_empty` 为必做防线**（四轮 #3 定案）：同步按钮拉候选 → 前端按只填空合并 → 提交。**capabilities 端点支持 `mode=fill_empty`（仅填空、不覆盖非 NULL）作为后端防线**，防绕过前端（curl/脚本）全量覆盖用户手填值。默认（无 mode）= 明确全量覆盖。
- **不扩展现有 `update` 模型端点**（PUT provider 带 models 数组，database.py:1493 只写 model_name/enabled/preprocessor/image_generation）：把能力字段塞进 models 数组会让每次 saveModelEdit 洗掉手动值或把 NULL 覆盖成有效值。
- 现有 GET 模型列表：返回新字段（前端展示），modalities 须 `json.loads` 为数组再返回。

### 4.5 路由接入（本次不实现，仅预留）
- `prepare_request_policy` 读模型元数据的接口留好，但**本次不接路由**（避免大改动）。多模态转发 / 分流 / 计费作为后续独立任务。
- **预留桩必须默认返回原逻辑**，未实现时不得误吞/改判请求。

### 4.6 `responses_*` 与新字段的关系
- 现表已有 `responses_streaming` / `responses_tool_types` 等能力字段，与新增 modalities 概念**重叠但语义不同**：
  - **`responses_*`**：来自供应商 API 实测反馈，**运行态验证**。
  - **`*_modalities` 等**：来自外部源聚合，**静态能力描述**。
- 两者并存；**路由决策以实测优先**（`responses_*` 为准，modalities 作兜底）。

## 8. 已确认口径 / 开放问题

**已确认（用户拍板 + 四轮评审 + 用户补充 review 定案）**：
1. **网络数据源必需**（models.dev / OpenRouter 为主），LiteLLM 本地**始终参与**合并。
2. **价格单位换算**统一转 `$/M token`；**仅考虑美元**。**归一化按字段名分支**：`per_token→×1e6`、`per_1k→×1e3`、已 $/M 勿二次换算、OpenRouter 先 `float()`。
3. **custom 重复同步只填空的字段**，保留用户改动；提供「覆盖全部」勾选可选；**"只填空"在前端实现**。
4. **价格合并（三轮定案）**：**三源并行**（models.dev ‖ OpenRouter ‖ LiteLLM）→ **≥3 取中位数** / **=2 取较高价**（+>20% WARN）/ **=1 单源**；embedding 单 input 价可参与；>10x 偏离记日志（接受降级）。

6. **admin 写库唯一走 `PUT capabilities`**（含 `mode=fill_empty` 后端防线），不扩展现有 PUT models 数组。~~custom-only 守卫~~ → 实现期改为 custom + auto 均可写（见文末「实现期偏离」）。

8. **砍 `metadata_sources` / `metadata_status` 两列**，依赖逻辑已逐条改为替代实现。

10. **两级缓存**：L1 全量 JSON 24h 惰性加载；L2 单模型 5–10min（键用归一化 model_id），只消费 L1 自发网。

## 9. 实现期偏离（Implementation Deltas）

以下各项在实现/评审阶段偏离了上文设计定案，**代码为准，本节为权威口径**。

### 9.1 `source` 枚举：`manual` → `custom`

- **变更**：模型来源枚举值由 `auto` / `manual` 改为 `auto` / `custom`。
- **落点**：`app/models.py` `ModelInfo.source` pattern `^(auto|custom)$`；`app/database.py` 迁移中 `UPDATE provider_models SET source = 'custom' WHERE source = 'manual'`（幂等，存量库自动升级）；前端 i18n 键 `models.makeCustom` / `models.sourceCustom`。
- **理由**：`manual` 与「手动填写能力字段」这一动作同名，容易与 auto 行也能手填的事实冲突；`custom`（自定义模型）描述的是**模型条目的归属**而非填写方式，语义更准。

### 9.2 `PUT capabilities`：custom-only → custom + auto 均可写

- **变更**：取消 `source == 'custom'` 写入守卫，auto 行的能力字段同样可通过该端点写入。
- **落点**：`app/router/admin.py` `update_model_capabilities`。
- **理由**：auto 行的数据所有权归上游 refresh。手填 auto 行的值会在下次 `refresh_provider_models` 时被覆盖 —— 这是可接受且可预期的语义（等价于「临时修正，待上游修好」），不必用 400 硬拦。若需永久保留，用户应显式「转为自定义模型」。
- **配套**：前端不再弹「保持 auto / 转为 custom」三选弹窗（原 `showConvertConfirm` 已删除），auto 行直接可编辑。
- **影响**：`§4.4`、`§6` 测试口径、`§8` 定案 6 已就地更新。

### 9.3 `PUT capabilities` 补登录鉴权

- **缺陷**：该端点声明了 `authorization: Optional[str] = Header(None)` 参数，但函数体从未调用 `require_admin_session` —— 未登录请求可改写任意模型的能力元数据。同文件只读端点 `metadata-candidates` 反而鉴权正确。
- **修复**：函数体首行补 `await require_admin_session(authorization)`。
- **回归**：`tests/test_metadata_api.py::test_put_capabilities_requires_login` 由 `assert 200 == 401` 转为通过。

### 9.4 `context_length` / `max_output_tokens` 跨源合并：`max()` → 按源优先级

- **变更**：跨源合并不再取 `max()`，改为**按源优先级取第一个有值的**：`models.dev` > `OpenRouter` > `LiteLLM`。逐字段独立 fallback（同一模型可能 `context_length` 由 models.dev 提供、`max_output_tokens` 落到 OpenRouter）。
- **落点**：`app/services/model_metadata.py` 新增 helper `_first_present(sources, field)`；`resolve_model_metadata` 的 Step 4 改用它，并改用独立的 `context_sources` 列表（不再复用 `price_sources`）。
- **理由**：三源报的**不是同一个量**，因此不可比 ——

  | 源 | 取的字段 | 语义 |
  |---|---|---|
  | models.dev | `limit.context` | 总窗口（输入 + 输出） |
  | OpenRouter | `context_length` | 总窗口 |
  | LiteLLM | `max_input_tokens` | **纯输入上限**（≤ 总窗口） |

  混进同一个 `max()` 等于假设它们可比。若 LiteLLM 的输入上限恰好最大，落库的就是一个「输入上限」却被当作「总窗口」展示；偏差方向恒为**偏大**。改为优先级 fallback 后，值的语义保持完整，低优先级源只在高优先级源无值时作为兜底，**不作为竞争候选**。
- **注意与定案 12 的关系**：定案 12「取典型/最大窗口」说的是**不做 per-modal 分档**（同一模型的文本窗口 vs 含音视频窗口），不是跨源取 max。本项不推翻定案 12，只是澄清它不适用于跨源合并。
- **价格合并不受影响**：`_merge_price` 仍取中位数 —— 价格三源报的是同一个量（$/M token），可比，中位数能抗单源离群值。
- **影响面**：`context_length` / `max_output_tokens` 目前**仅用于展示**（`grep` 确认 `app/router/` `app/core/` `app/protocols/` `app/adapters/` 中除 `admin.py` 的字段白名单外无运行时读取），因此本次修正只影响 admin UI 显示的准确性，无截断 / 拒绝 / 计费行为变化。**若将来接入输入预算校验或超窗截断，本项从「显示准确性」升级为正确性前提。**
- **回归**：`tests/test_model_metadata.py` 新增 4 例（优先级压制更大的低优先级值 / 落 OpenRouter / 落 LiteLLM / 逐字段独立 fallback）；原 `test_resolve_context_length_prefers_largest_typical_window` 更名为 `test_resolve_context_length_is_a_single_scalar_window`（旧名描述的是被推翻的实现而非定案本身）。反向验证：改回 `max()` 后 4 例中 3 例失败（第 4 例仅单源，`max()` 下无从混合，符合预期）。
