## 🟥 严重问题（必须修）

### 1. 字段命名：`*_modals` → `*_modalities`（全篇）

**位置**：DB 列名 `input_modals` / `output_modals`，全文 30+ 处。

行业通用术语是 **modalities**（模态）。`modals` 在英文语境里指"模态框"（modal dialog），语义歧义严重。一旦 DB 列名落地，改名成本极高（SQLite `ALTER TABLE RENAME COLUMN` 需 3.25+ 且要写迁移脚本）。

**建议**：改为 `input_modalities` / `output_modalities`，同步修正文档描述。

---

### 2. `metadata_status` 语义不明

**位置**：§3.1、§2.3 末尾。

文档说该字段区分"真无价格" vs "源解析失败"，但：
- DEFAULT 是 `''` — 空串代表什么？"尚未采集"？
- §4.2 提到 `'pending'` — 代表"源解析失败"还是"待重试"？
- 哪个值代表"真无价格"？未定义。

**建议**：明确枚举取值：

| 值 | 含义 |
|---|---|
| `''`（空串） | 尚未采集（初始状态） |
| `'pending'` | 已尝试但源解析失败/超时，可重试 |
| `'resolved'` | 至少一源成功返回，结果已写入 |
| `'no_pricing'` | 所有源均明确无价格信息（真无价格） |

---

### 3. models.dev 来源可靠性声明缺失

**位置**：§2.2。

models.dev 官方与第三方指南均明确 **"Do not treat this as runtime truth"** — 数据可能不准确、不实时。设计将其列为**主源**却无免责声明或精度预案。

**建议**：在 §2.1 / §2.2 补一句：**"models.dev 数据仅供参考，不保证与供应商实际 API 一致；高精度场景（尤其计费）应以供应商官方定价为准，元数据仅作缺省估算。"**

## 🟧 中等问题（建议改）

### 4. 匹配工具失败时无回退链

**位置**：§2.3 流程图、§4.1。

流程图显示三源并行，但未定义顺序与回退：models.dev 失败是否自动走 OpenRouter？两网络源都失败是否降级 LiteLLM？三源全失败返回什么？

**建议**：明确回退链 **models.dev → OpenRouter → LiteLLM**（逐级降级，后一源仅在前一源无候选时启用），或在流程图中加决策分支。

---

### 5. 缓存体系两层关系未说明

**位置**：§4.1、开放问题 §1。

文档存在两个缓存：全局全量 JSON（24h TTL，只在"开放问题"提到）与单模型匹配结果（5–10min TTL）。若全局 JSON 24h 未刷新，单模型缓存过期后重查仍拿到旧数据 —— 5min TTL 实际无意义。

**建议**：在 §4.1 显式定义两级缓存：
- **L1**：全量 JSON 列表（models.dev / OpenRouter），TTL 24h，惰性加载
- **L2**：单模型匹配结果，TTL 5–10min，写库成功后主动失效对应键
- L1 过期才触发网络请求；L2 只消费 L1，绝不自行发网络请求

---

### 6. M1 范围不明确：新字段如何填充？

**位置**：§7 里程碑。

M1 为"DB 迁移 + 新字段读写"，但迁移后字段全是 NULL/`[]`。M2（匹配工具）未完成时，字段靠什么填充？只能前端手填？

**建议**：M1 改为 **"DB 迁移 + 字段读写 + 前端手动填写（manual 模型）"**；或把 LiteLLM 本地源提前到 M1 作为零网络成本的基线填充。

---

### 7. `context_length` 单一标量的局限性

**位置**：§1.3。

部分模型上下文随模态变化（如 Gemini 系列文本窗口与含音频/视频时不同），单标量会丢精度。

**建议**：补备注：**"当前为单一标量，取各源最保守值；后续可扩展为 `context_lengths` JSON 按模态细化。"**

## 🟡 小问题（可选）

### 8. models.dev 端点补充

`https://models.dev/api.json` 路径已验证正确（上游 repo README 确认）。另有 `models.json`（模型维度，provider-agnostic）与 `catalog.json`（合并）两个端点未提及。

**建议**：补一句 **"主用 `api.json`（provider 维度）；必要时交叉引用 `models.json`（模型维度）。"**

### 9. `responses_*` 与新字段的关系

现表已有 `responses_streaming` / `responses_tool_types` 等能力字段，与新增 modalities 概念重叠但语义不同，文档未说明。

**建议**：补充 **"`responses_*` 来自供应商 API 实测反馈（运行态验证）；`*_modalities` 等来自外部源聚合（静态能力描述）。两者并存，路由决策以实测优先。"**

### 10. 模型 ID 归一化复杂度被低估

**位置**：§2.3 / §4.1 `_normalize_model_id`。

跨源 ID 形态差异大：`gpt-4` / `openai/gpt-4` / `gpt-4-1106-preview`；`claude-3-opus-20240229` / `anthropic.claude-3-opus`。这是非平凡的实现难点。

**建议**：给出规则优先级：① 去 provider 前缀（`vcp-`、`openai/`）② 去日期/版本后缀（`-latest`、`-20240229`、`-0125`）③ 小写 ④ 无法匹配时记日志、不阻断。

### 11. 价格显示格式

**位置**：§5.2。

`$/M token` 多为小数（如 `$0.15`），"千分位"格式不适用（`0,150` 是错的）。

**建议**：明确 **"价格显示 `$0.15/M`（两位有效小数）；context 显示 `8K` / `128K`。"**

### 12. discovery 的 INSERT 语句需同步

**位置**：`app/services/discovery.py:174`

```sql
INSERT OR IGNORE INTO provider_models (provider_id, model_id, model_name, enabled, source) VALUES (?, ?, ?, 1, 'auto')
```

迁移后新行靠 DEFAULT 填充可用，但 M2 接入后此语句需扩展为写入 metadata 字段，否则 discovery 新发现的模型不会自动带能力数据。

**建议**：在 §4.2 加提醒。

## ✅ 设计到位、值得肯定的部分

1. **价格单位归一化按字段名分支** —— 已实测三源单位差异，方案正确
2. **模态白名单"宁漏勿虚"** —— 避免虚报能力导致错误路由
3. **sync-metadata 默认只返回候选不写库** —— 预览机制杜绝意外覆盖
4. **manual 模型"只填空"+ 覆盖全部开关** —— 用户改动始终优先
5. **独立 capabilities 端点 + manual-only 守卫** —— 不扩展现有 PUT models 数组，规避静默清空
6. **批量预取（`asyncio.gather` + Semaphore(4)）** —— 避免循环内逐模型 await
7. **测试边界用例全面** —— 价格单位归一化、网络超时降级、PUT 覆盖保护三项尤其关键
8. **XSS 防护显式要求** —— 外部候选值回填前 HTML 转义
