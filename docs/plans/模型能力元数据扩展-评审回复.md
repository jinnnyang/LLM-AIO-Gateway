## 一、先更正我自己的两处错误

评审过程中我提出过两个质疑，事后核实都是我错，在此撤回：

**1. 我质疑过报告对 `tests/test_discovery_metadata.py` 的用例统计**

我当时用 `grep` 数 `def test_`，只数出 1 条，据此认为报告「~20+ 高质量测试」的评级虚高。实际 `pytest` 收集到 **28 条** —— 我的 grep 模式漏掉了 class 内缩进的形式。报告的统计是准确的，是我错怪了。

**2. 我断言过「Python 3.11 已移除 `asyncio.Semaphore` 的 loop 绑定」**

错。3.11 只是把绑定**时机**从构造推迟到首次 `acquire()`，绑定本身依然是永久的。据此把信号量裸放到模块级会出现「单文件跑全绿、合跑全红」，报：

```
RuntimeError: ... is bound to a different event loop
  File "Lib\asyncio\locks.py", line 379, in acquire
```

所以 P2-2 的修复必须做 per-loop 惰性初始化（`weakref.WeakKeyDictionary`），这不是「未来兼容项」而是当下的正确性要求。

### P2-1 — 已修

改成两层锁：状态锁**永不跨** `fetcher()`，另有每源一把刷新锁。三分支策略：新鲜直接返回；过期时用 `acquire(blocking=False)`，抢不到的**直接拿旧 catalog 走**（读者永不阻塞）；冷启动才阻塞，且只放一个请求出去。

冷启动特意**不做** non-blocking —— 返回 `{}` 会让每个模型都解析成「无元数据」，而这个空结果会被写进 L2 缓存 5 分钟。那是把性能问题换成正确性问题。

补充一个减轻事实：L1 的 TTL 是 86400s（不是 L2 的 300s），且 catalog 全局共享而非 per-model。所以竞争窗口是**每天首次刷新时串行等一次拉取**，比报告描述的「刷新时秒级卡顿」暴露面小。

### P2-2 — 已修

报告指出得对，而且比报告写的更严重：`refresh_all_providers` 并发 4 个 provider，每个又各自 new 一个 `Semaphore(4)` → **实际 16 并发**。两处注释都声称 4，是注释在撒谎，不是「缺注释」。

### P2-4 — 驳回

`app/services/discovery.py:38` 的 `_has_any_metadata()` 是**两段 OR**：先查 5 个标量字段（`context_length` / `max_output_tokens` / 三个价格）任一非 `None` 即 `return True`，之后才查模态。报告设想的「有价格但无模态声明 → 被判全空跳过写入」不可能发生。

另外报告建议的「默认填 `text`」违反定案 5「宁漏勿虚」——猜出来的元数据比空值更危险。

### P3-5 — 已修

改成按源优先级取第一个有值的（models.dev > OpenRouter > LiteLLM），逐字段独立 fallback。理由是三源报的**不是同一个量**：

| 源 | 字段 | 语义 |
|---|---|---|
| models.dev | `limit.context` | 总窗口（含输出） |
| OpenRouter | `context_length` | 总窗口 |
| LiteLLM | `max_input_tokens` | **纯输入上限** |

混进同一个 `max()` 等于假设三者可比，偏差方向恒为偏大。价格合并未动 —— 价格三源报的是同一个量（$/M token），可比，中位数抗离群是对的。

顺带处理了一个文档陷阱：定案 12「取典型/最大窗口」原文讨论的是 per-modal 分档，不是跨源取 max，但字面读起来完全支持 `max()`。已在定案 12 加澄清并新增 §9.4，避免后人「照定案」改回去。

### P3-6 — 已修

报告只提到清旧 key，我另外**把新 id 也清了**：改名前若有人查过 `new-name`（当时不存在），L2 里缓存的是空结果，改名后会继续供 300 秒。

失效动作放在事务**外**：块内失效若后续回滚，会出现「没发生的改名清掉了活跃缓存」。
