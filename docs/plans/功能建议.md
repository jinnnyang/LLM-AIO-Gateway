# LLM AIO Gateway 功能建议

按小工具、个人向的定位过滤，以下功能按优先级整理。

## 必要功能

### 1. 请求/响应查看器
- 现状: `request_records` 表只记了 model/username/success/tokens，admin 面板 stats 页能看到聚合，但看不到某条具体请求的完整 body。
- 目标: 在 admin 面板加一个"最近 N 条请求"列表，点开看完整入参/出参/routing 详情/错误信息。
- 落地:
  - 新增 `request_logs` 表。
  - `app/router/proxy.py` 在四个端点的成功/失败路径统一调用 `_log_request_detail()` 写入。
  - 新增 `/admin/request-logs` 列表/详情/清空/按 endpoint 过滤 API。
  - admin SPA 新增"请求日志"侧边栏，渲染 JSON（高亮 + 折叠）。

### 2. 导出/导入配置
- 现状: `providers / routing_rules / fallback_policies` 只能一条条手动加。
- 目标: admin 面板增加"导出配置"和"导入配置"按钮，生成一个 JSON 文件。
- 落地:
  - 新增 `/admin/config/export` 返回 JSON（默认脱敏 api_key）。
  - 新增 `/admin/config/import` 接收 JSON，按策略（skip/replace/merge）处理。
  - admin SPA 在"系统设置"区块放两个按钮 + 一个策略下拉。

## 差异化功能

- Anthropic Prompt Caching 透传 + 命中率统计
- 可配置超时/重试
- 精确匹配响应缓存
- Prompt 模板库 + 变量插值
- 本地 Ollama 适配器
- 多模态扩展（PDF、音频）
- Token 用量看板 + 单价换算
- 轻量 A/B 对比

## 可以跳过的

多租户、SSO、审计日志、Webhook、自动评测、Helm chart、SDK 矩阵、批处理 API、影子流量、限流、配额、计费、Prometheus 全部跳过。

## 远期愿景 / Dream（仅愿景，无实现计划）

### DAG 编排中间件架构
> 2026-08-26 用户提出的远期架构愿景。**列为 goal/dream，不列具体计划**，等节点类型多到编排成为痛点时再评估。
>
> **补充（2026-08-26）**：用户 token 用量大 + 客户跨领域 → **压缩器（上下文/提示词压缩）与 skill 注入是近期刚需，不是远期**。但这两者是**独立处理节点**，可作为轻量中间件先接入现有管线（类似 preprocessing 图片描述），**不依赖 DAG**。DAG 的定位是「统一编排层」，在节点 ≥4-5 种、编排成为真实痛点时才值得重构。**单点能力先行，统一编排后置。**

- **构想**：将模型分配过程运行在**一张有向无环图（DAG）**上。图的节点包括：
  - 直连模型（models）
  - 聚合端点（combos）
  - 过滤器（filters）
  - 压缩器（用户提示词压缩 / 上下文压缩）
  - 注入器（prompt 注入 / skill 注入）
  - 拦截器（模型生成内容安全审查）
  - 记忆系统（检索用户状态 / 跨领域知识）
  - …未来将要实现的各种处理单元
- **核心抽象**：每个节点**接受一个内部统一对象，输出一个内部统一对象**；节点间通过统一对象传递数据。
- **编排**：现有「路由规则」演化为**描述这些节点如何连接**的编排层（图定义），而非硬编码逻辑。
- **真实价值锚点——图像分流**：现状图像分流逻辑已散落 proxy.py 多处（`has_image_content` 检测、`preprocess_messages` 预处理、`_target_supports_native_vision` 目标能力判断、image_bridge 接管、fallback 特判），靠一堆 helper + 条件分支拼装。DAG 可将「图像→视觉模型、文本→文本模型、安全→拦截器、用户状态→记忆检索」这类分流**统一表达为图的边**，消除散落逻辑。
- **与现状关系**：现有路由规则（match→target）与 fallback chain（线性链）是 DAG 的**特例**（无分支、无自定义节点）。DAG 是更一般化的终局抽象。
- **概念收敛——fallback 即 combo**：现有「fallback（失败/可用性切换）」与「combo（按路由策略聚合）」在 DAG 中**收敛为同一个「多选一」节点**，仅选择策略字段不同（fallback=按失败/可用性，combo=按 fill-first/priority 路由策略）。同理，直连模型是「单叶子」节点。DAG 让不同入口概念统一为同类节点。
- **价值**：多模态转发、分流、计费、压缩、注入等能力可统一为可组合节点，避免逻辑散落在各端点。
- **最大投入点**：内部统一对象的地基定义（消息 / 模型 / 元数据 / usage / 计费 / 上下文 / 会话），以及可观测性（每节点 trace）与向后兼容迁移。
- **触发条件**：当节点类型超过当前「直连 + fallback」两种、且编排成为真实痛点时，才值得重构为 DAG。**「散落即信号」**——当某类分流逻辑（如图像分流）开始在 proxy 各端点散落、靠 helper + 条件分支拼装、新增节点需同时改多处时，即重构信号。在此之前用轻量扩展（读模型元数据 + prepare_request_policy 加判断）满足需求。
